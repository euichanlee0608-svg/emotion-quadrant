# 감정의 사분면

“기분이 안 좋다”로 뭉뚱그려지는 감정에, 좀 더 정확한 이름을 붙여 보는 웹앱.

한국어 감정단어 **434개**를 의미 계층(대분류 16 → 중분류 74 → 단어)으로 묶고,
그 트리를 **세 걸음**에 걸어 내려간다. 매 화면은 사분면이고, 놓인 것들의 실제 평정값으로
좌표를 잡는다.

```
0단계  어느 갈래인가      16개 대분류        가로 기분(쾌-불쾌) × 세로 세기(활성화)
1단계  그 안에서 어떤 결   그 대분류의 중분류   가로 기분 × 세로 세기 (그 갈래 안에서 다시 스케일)
2단계  그중 어떤 말        그 중분류의 단어들   가로 세기 × 세로 흔한 말 ↔ 잘 안 쓰는 말
```

예: `기쁨 › 터져 나오는 기쁨 › 희열`, `두려움·불안 › 초조한 › 불안하다`.

요즘 기분이나 상황을 자연어로 적으면 그 글에서 감정 후보를 찾아 주기도 한다.

## 왜 좌표 줌이 아니라 의미 트리인가

처음엔 쾌-불쾌·활성화 좌표를 재귀적으로 좁히는 방식이었다. 써 보니 두 가지가 깨졌다.

1. **좌표 이웃 ≠ 의미 이웃.** `외롭다`(v2.28/a2.76)와 `지루하다`(v2.64/a2.14)는 좌표 거리가
   0.72로 붙어 있지만 전혀 다른 감정이다. 좁혀 들어가면 "점점 정확한 말"이 아니라
   "좌표만 가까운 남의 감정"이 나왔다.
2. **데이터 공간의 모서리에서 막힌다.** `기쁘다`(v 5.94)를 고르면 그보다 쾌-불쾌가 높은 단어가
   434개 중 6개뿐이라 사분면 하나가 통째로 비었다. "더 센 기쁨"으로 갈 길이 없었다.

논문도 좌표가 아니라 의미로 묶었다 — 225개를 뜻이 비슷한 것끼리 87범주로 나누고 각 범주의
대표어를 뽑았다. 다만 **그 범주 구성원 목록은 논문에 실려 있지 않다.** 그래서 434개 전체에
의미 계층을 직접 붙였다(`source/taxonomy.json`). 이건 논문 내용이 아니라 이 사이트의 분류다.

트리로 바꾼 뒤 **434개가 전부 3단계 만에 도달 가능**해졌다(좌표 줌 시절엔 299종에서 멈췄다).

## 데이터 출처

박인조·민경환 (2005). 「한국어 감정단어의 목록 작성과 차원 탐색」.
*한국심리학회지: 사회 및 성격*, 19(1), 109–129.

부록 1의 감정단어 434개와 네 가지 평정값(원형성·친숙성·쾌-불쾌·활성화, 모두 7점 척도 평균)을
그대로 썼다. **뜻풀이와 의미 분류는 이 사이트에서 붙인 것으로 논문 내용이 아니다.**
결과 화면에서도 둘을 나눠 표시한다.

### 추출 정확도

논문 표 4가 434개 단어의 쾌-불쾌·활성화를 1점 구간별로 집계해 두었는데, 추출 결과가
**두 차원 모두 정확히 일치**한다(`source/build_data.py`가 매번 이 체크섬을 확인).

| 구간 | 쾌-불쾌 (논문 / 추출) | 활성화 (논문 / 추출) |
|---|---|---|
| 1~1.99 | 39 / 39 | 1 / 1 |
| 2~2.99 | 216 / 216 | 42 / 42 |
| 3~3.99 | 57 / 57 | 129 / 129 |
| 4~4.99 | 44 / 44 | 143 / 143 |
| 5~5.99 | 75 / 75 | 111 / 111 |
| 6~6.99 | 3 / 3 | 8 / 8 |

알려진 원문 이슈 두 가지:

- 부록에 `감홍`으로 인쇄돼 있으나 感興(**감흥**)이다. 앱에서는 교정해 표시한다.
- 논문 본문은 대표단어를 **87개**라 하는데 부록의 `*` 표시는 **86개**뿐이다. 원문 자체의
  불일치라 임의로 채우지 않았고, 화면 구성에는 쓰지 않는다(표시만 한다).

## 자연어 입력 → 감정 찾기

| | 언제 | 무엇 |
|---|---|---|
| 1 | 기본(공개 사이트 포함) | **Supabase Edge Function** → Gemini `gemini-3.1-flash-lite`(가장 싼 모델). 키는 `app_secrets`에만 |
| 2 | 제미나이를 못 쓸 때 | **맥미니 로컬 모델 대기열** — 아래 참고 |
| 3 | 그것도 안 되면 | **`localMatch`** — 순수 클라이언트 글자 매칭. 오프라인·서버 장애에도 동작 |
| — | 로컬에서 열었을 때만 | 맨 앞에 로컬 Ollama 를 직접 시도(토큰 0) |

**사용자에게는 진행중 / 완료 / 실패만 보여 준다.** 어떤 모델이 처리했는지, 중간에 어느 경로가
실패했는지는 화면에 내지 않는다 — 결과가 잘 나왔는데도 "실패했나?" 하고 불안해진다.
자세한 경로는 텔레그램 알림과 콘솔에만 남는다(`browser_check.py` 가 노출 여부를 검사한다).

### 제미나이가 떨어지면 맥미니가 대신 처리한다

공개 사이트가 맥미니를 직접 부를 수는 없다(위 참고). 그래서 **방향을 뒤집었다** —
서버가 맥미니를 부르지 않고, **맥미니가 서버에 일감을 가지러 온다.** 포트 개방·터널·고정 IP가
전혀 필요 없다.

```
브라우저 → Edge Function → 제미나이 (성공하면 여기서 끝)
                    ↓ 실패 / 일일 캡 소진
              emoquad_jobs 에 작업 등록  +  텔레그램 알림
                    ↑ claim              ↓ 브라우저가 job 으로 결과를 물어봄
        맥미니 워커(launchd) — Ollama 로 처리 후 finish
```

| | |
|---|---|
| 워커 | `worker/emoquad_worker.py`, launchd `com.leechan.emoquadworker` |
| 상주 비용 | **RSS 19MB · CPU ~0%.** 모델은 요청이 올 때만 로드되고 기본 5분 뒤 해제된다 |
| 폴링 | 일이 있었으면 5초, 조용하면 60초 간격 |
| 인증 | `claim`/`finish` 는 워커 토큰으로만. 토큰은 `app_secrets` + `worker/.env`(깃 제외) |
| 실측 | 큐 등록 → 결과까지 약 15초 |

품질은 제미나이보다 낮다(예: `슬프다, 불안하다` vs `속상하다, 부럽다, 열등감`).
한도가 떨어졌을 때 아무것도 못 주는 것보다는 낫다는 판단이다.

### 왜 브라우저가 로컬 모델을 직접 못 부르나

실제로 시도해 보고 두 가지 이유로 접었다.

1. **브라우저가 막는다.** `https://` 페이지에서 `http://127.0.0.1:11434` 로 보내는 요청은
   크롬이 차단한다(mixed content / Private Network Access). Ollama 쪽에
   `OLLAMA_ORIGINS` 로 사이트 주소를 열어 줘도 브라우저 단에서 끊긴다 — 헤드리스로
   실측했고 `Failed to fetch` 였다. 즉 공개 사이트가 사용자의 로컬 모델을 부르는 건
   정적 사이트로는 구조적으로 불가능하다.
2. **품질도 떨어진다.** 같은 문장("열심히 준비한 게 잘 안 됐는데, 남들은 다 잘 풀리는 것 같아서…")에
   `exaone3.5:7.8b` 는 `아쉽다, 슬프다, 부럽다` 에 그쳤고, `gemini-3.1-flash-lite` 는
   `속상하다, 부럽다, 열등감, 답답하다, 착잡하다` 로 상황의 핵심(열등감)을 짚었다.

로컬 모델 경로는 코드에 남아 있고, `python3 -m http.server` 로 로컬에서 열면 그대로 쓰인다.
공개 사이트에서 로컬 모델을 쓰는 길은 위의 **대기열 방식**으로 따로 열어 두었다.

### 처리량

| | |
|---|---|
| 제미나이 키 | 4개(순차 폴백 — 앞 키가 실패할 때만 다음으로) |
| 앱 자체 하드 캡 | **하루 300건** (`emoquad_hit`, Edge Function 안) |
| 1건당 | 입력 약 3,700 토큰(434개 단어 목록이 대부분) + 출력 약 100 토큰 |
| 캡 소진 시 | 에러가 아니라 맥미니 대기열로 넘어간다 |

### 동작 확인 알림

분석이 끝나면 입력 글과 추천 단어를 텔레그램(COT봇)으로 한 줄 보낸다.
서버가 처리한 경우는 Edge Function 이 직접 보내고, 로컬 모델·폴백이 처리한 경우는
클라이언트가 `{action:"notify"}` 로 중계한다(이 경로는 모델을 부르지 않아 캡을 쓰지 않는다).

어느 쪽이든 **반드시 434개 안의 단어만** 돌려준다. 모델이 목록 밖의 말을 지어내면
서버와 클라이언트 양쪽에서 버린다 — 그래야 결과 화면의 논문 평정값과 앞뒤가 맞는다.

Edge Function은 비로그인 공개(`verify_jwt=false`)라 서버측 일일 캡을 건다
(`emoquad_usage` 테이블 + `emoquad_hit()` security-definer RPC, service_role 전용).
함수 원본 사본은 `supabase/functions/emoquad-analyze/index.ts`.

## 구조

빌드 도구 없는 정적 사이트. 전부 상대경로이고 프론트에 키가 없다.

```
index.html   마크업 + 전체 CSS + 방문 비콘
engine.js    의미 트리 탐색 (레벨·배치·축 이름·로컬 매칭) — 브라우저 없이 테스트 가능
app.js       화면 렌더와 이벤트
analyze.js   자연어 → 감정 후보 (로컬 모델 → Edge Function → 로컬 매칭)
data.js      단어 434개 + 의미 계층 (source/build_data.py 로 생성 — 직접 고치지 말 것)
source/      논문 추출 원자료 · 뜻풀이 · taxonomy.json · 생성 스크립트
tests/       엔진 회귀 테스트, 브라우저 검증 스크립트
```

## 검증

```bash
node --check app.js && node --check engine.js && node --check analyze.js
node tests/engine_test.mjs        # 데이터 체크섬 + 의미 계층 + 배치 + 434개 전수 도달
python3 source/build_data.py      # data.js 재생성이 재현되는지
```

브라우저 검증(헤드리스 크롬 CDP, 데스크톱 1280 + 모바일 390 두 뷰포트):

```bash
python3 -m http.server 8777 &
python3 -m venv /tmp/cdpvenv && /tmp/cdpvenv/bin/pip install websocket-client
/tmp/cdpvenv/bin/python tests/browser_check.py http://127.0.0.1:8777/index.html
```

`--window-size`는 이 Mac의 크롬에서 500px 미만으로 안 내려가므로, 진짜 390px 검증은
CDP `Emulation.setDeviceMetricsOverride`로 한다. 자세한 건 메모리 `reference-webapp-playbook` §3.

## 범위 밖

- **한/영 토글 없음.** 434개 감정단어의 미묘한 차이는 번역하면 그대로 뭉개진다.
  UI는 한국어로만 두고, 푸터에 이 앱이 뭔지 설명하는 영어 문단만 넣었다.
- 심리 검사·진단이 아니다. 감정에 이름을 붙여 보는 어휘 도구다.
