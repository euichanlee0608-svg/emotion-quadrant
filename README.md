# 감정의 사분면

“기분이 안 좋다”로 뭉뚱그려지는 감정에, 좀 더 정확한 이름을 붙여 보는 웹앱.

한국어 감정단어 **434개**를 평면에 실제 평정값 그대로 놓는다. 세로는 늘 원형성
「누구나 쓰는 말 ↔ 잘 안 쓰는 정확한 말」이고, **가로축은 고정이 아니다** — 단어를 고를 때마다
남은 후보에서 쾌-불쾌와 활성화 중 실제로 더 잘 갈리는 쪽을 골라 사분면을 다시 세운다.
단어를 하나 고르면 **그 단어가 가로 한가운데 · 세로 맨 위**에 놓이고, 화면은 그보다 정확한
말들로 다시 채워진다. 축 이름도 좁아진 구간에 맞춰 다시 붙는다
(`안 좋음 ↔ 좋음` → `참담함 ↔ 괴로움`, `누구나 쓰는 말 ↔ 잘 안 쓰는 말` → `흔한 말 ↔ 드문 말`).
이 사이클을 4~6번 돌면 평소엔 잘 안 쓰던, 그러나 지금 상태에 더 정확한 단어에 닿는다.

단어를 한 번 누르면 뜻이 뜨고, 읽어 본 뒤 좁힐지 / 여기서 멈출지 고른다.

## 데이터 출처

박인조·민경환 (2005). 「한국어 감정단어의 목록 작성과 차원 탐색」.
*한국심리학회지: 사회 및 성격*, 19(1), 109–129.

부록 1의 감정단어 434개와 네 가지 평정값(원형성·친숙성·쾌-불쾌·활성화, 모두 7점 척도 평균)을
그대로 썼다. **뜻풀이는 이 사이트에서 붙인 것으로 논문 내용이 아니다.**

### 추출 정확도

논문 표 4가 434개 단어의 쾌-불쾌·활성화를 1점 구간별로 집계해 두었는데, 추출 결과가
**두 차원 모두 정확히 일치**한다(`source/build_data.py`가 매번 이 체크섬을 확인).

| 구간 | 쾌-불쾌 (논문 / 추출) | 활성화 (논문 / 추출) |
|---|---|---|
| 1~1.99 | 39 / 39 | 1 / 1 |
| 2~2.99 | 216 / 216 | 42 / 42 |
| 3~3.99 | 57 / 57 | 129 / 129 |
| 4~4.99 | 44 / 44 | 143 / 143 |
| 5~5.99 | 75 / 75 | 111 / 111 |
| 6~6.99 | 3 / 3 | 8 / 8 |

알려진 원문 이슈 두 가지:

- 부록에 `감홍`으로 인쇄돼 있으나 感興(**감흥**)이다. 앱에서는 교정해 표시한다.
- 논문 본문은 대표단어를 **87개**라 하는데 부록의 `*` 표시는 **86개**뿐이다. 원문 자체의
  불일치라 임의로 채우지 않았다. 대신 화면에 띄울 단어는 `*` 표시가 아니라
  **원형성(연속값)** 순으로 고른다 — 이쪽이 전수 검증된 값이다.

## 구조

빌드 도구 없는 정적 사이트. 전부 상대경로이고 백엔드가 없다.

```
index.html   마크업 + 전체 CSS + 방문 비콘
app.js       사분면 줌 엔진 (좌표 계산·단어 선택·축 라벨·배치 보정)
data.js      단어 434개 (source/build_data.py 로 생성 — 직접 고치지 말 것)
source/      논문 추출 원자료 + 뜻풀이 원본 + 생성 스크립트
tests/       엔진 회귀 테스트, 브라우저 검증 스크립트
```

### 가로축을 왜 고정하지 않는가

축을 획일화하면 막힌다. 가로를 계속 쾌-불쾌로 두면 `기쁘다`(v 5.94)를 고르는 순간
1사분면 후보가 1개가 된다 — 쾌-불쾌가 기쁘다보다 높은 단어가 434개 중 6개뿐인,
데이터 공간의 모서리이기 때문이다. 반대로 계속 활성화로 두면 0단계에서
좋은 감정과 나쁜 감정이 안 갈린다.

기쁨 계열(v≥5.0, 78개) 안에서 각 축이 퍼진 폭을 보면 이유가 분명하다.

| 축 | 전체 434개 | 기쁨 계열 78개 |
|---|---|---|
| 쾌-불쾌 | 표준편차 1.280 (가장 잘 갈림) | 폭 1.24 (거의 안 갈림) |
| 활성화 | 표준편차 0.977 | **폭 4.76** (편안하다 1.90 ~ 열광하다 6.66) |

`기쁘다`보다 쾌-불쾌가 높은 단어는 6개지만 활성화가 높은 단어는 44개다.
그래서 `chooseAxis`가 매 단계 **퍼짐(전체 표준편차로 정규화) × 앵커 기준 좌우 균형**으로
축을 다시 고른다. 전체에서는 쾌-불쾌가 이기므로 0단계는 자연히 「안 좋음 ↔ 좋음」이 되고,
기쁨 쪽으로 좁힌 뒤에는 활성화가 이겨 「차분한 ↔ 터질 듯한」이 된다.

화면에 안 쓰인 축은 앵커 기준 밴드로 **누적해서** 좁힌다(넓어지는 일은 없다). 이게 없으면
가로축이 바뀌는 순간 이전에 좁혀 둔 감정 방향이 풀려, 기쁨을 파고들다 `무섭다·화나다`가
튀어나온다(실제로 그랬다).

세로축은 늘 원형성이다. 어떤 단어를 골라도 그 아래엔 늘 단어가 남아 막히지 않고,
"점점 정확한 말로 내려간다"는 목적이 축에 그대로 드러난다.
논문도 같은 방향을 가리킨다 — MDS 2차원은 활성화가 아니라 「타인 초점적–자기 초점적」이고,
본문은 "제 2차원으로 '활성화 수준'은 나오지 않았다"고 적는다.

### 엔진 요약 (`app.js`)

- `view = {cx, cy, rx, ry}` — 지금 보고 있는 (쾌-불쾌, 원형성) 구간.
  0단계는 가로 원점을 척도 중립값 4.0, 세로를 원형성 범위(2.35~5.98)의 한가운데에 둔다.
- 단어 선택: 시야 안 · 안 지나온 단어를 사분면별로 나눠 **원형성 높은 순**으로 돌아가며 집되,
  정규화 좌표에서 최소 간격(`SEP_X`/`SEP_Y`)을 두는 것만 통과시킨다. 최대 12개.
- **심화 보장**: 고른 단어를 세로축 **맨 위**에 두므로, 화면에 남는 건 늘 그보다 정확한 말이다.
  예전에는 "덜 흔한 말만 남긴다"는 숨은 제약으로 이걸 했는데, 지금은 축이 직접 보여 준다.
  (제약이 아예 없던 시절 경로는 `1위 → 63위 → 6위 → 19위 → 29위 → 4위`로 제자리걸음이었다.)
- 배치 보정(`relaxChips`): 칩 폭은 글자 수·화면 폭에 따라 달라져 정규화 좌표만으론 겹침을
  못 막는다. 그려진 뒤 **실제 픽셀**로 보드 안에 클램프하고 겹친 쌍을 밀어 뗀다.
- 줌(`fitView`): 고른 단어를 새 원점으로 삼고, **남은 후보가 직전의 35%가 되도록** 반경을 찾는다.
  고정 비율(예: 항상 0.55배)로 좁히면 안 되는 이유는 데이터가 한쪽에 쏠려 있기 때문이다 —
  불쾌·고활성은 175개인데 쾌·저활성은 35개뿐이라, 고정 비율이면 어느 방향을 골랐느냐에 따라
  세분화 깊이가 딴판이 된다. 후보 수를 기준으로 삼으면 밀도와 무관하게 균일해진다
  (측정: 화면당 빈 사분면 평균 0.70개).
- 종료: 띄울 칩이 3개 미만이거나 `MAX_DEPTH`(7단계)에 닿으면 결과 화면으로.
  보통 3~5단계, 종착 단어 299종. 흔한 말에서 출발하면 길고, 이미 정확한 말에서 출발하면 짧다.
  지도 화면의 '여기서 멈추기'로 언제든 그 자리에서 끝낼 수도 있다(뜻 카드를 열지 않아도 된다).

## 검증

```bash
node --check app.js
node tests/engine_test.mjs        # 데이터 체크섬 + 배치 규칙 + 경로 순회
python3 source/build_data.py      # data.js 재생성이 재현되는지
```

브라우저 검증(헤드리스 크롬 CDP, 데스크톱 1280 + 모바일 390 두 뷰포트):

```bash
python3 -m http.server 8777 &
python3 -m venv /tmp/cdpvenv && /tmp/cdpvenv/bin/pip install websocket-client
/tmp/cdpvenv/bin/python tests/browser_check.py http://127.0.0.1:8777/index.html
```

`--window-size`는 이 Mac의 크롬에서 500px 미만으로 안 내려가므로, 진짜 390px 검증은
CDP `Emulation.setDeviceMetricsOverride`로 한다. 자세한 건 메모리
`reference-webapp-playbook` §3.

## 범위 밖

- **한/영 토글 없음.** 434개 감정단어의 미묘한 차이는 번역하면 그대로 뭉개진다.
  UI는 한국어로만 두고, 푸터에 이 앱이 뭔지 설명하는 영어 문단만 넣었다.
- 심리 검사·진단이 아니다. 감정에 이름을 붙여 보는 어휘 도구다.
